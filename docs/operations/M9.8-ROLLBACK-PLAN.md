## 1. Rollback Strategy & Emergency Triggers

An immediate automated or manual rollback is initiated if any of the following triggers occur:
1. **API Unavailability:** `https://api.eozka.com/healthz` or `/readyz` fails to respond with HTTP 200 within 60 seconds post-deployment.
2. **Database Failure:** Persistent connection errors, connection pool exhaustion, or migration failure on Supabase.
3. **Broker Failure:** Upstash Redis connection failure or stream consumer degradation.
4. **Authentication Failure:** Inability to authenticate existing platform administrator or issue valid JWTs.
5. **CORS Regression:** Inability for `https://kelvin-orpin.vercel.app` to execute authenticated preflight and API requests.
6. **Security Violation:** Any unexpected outbound scanner traffic violating target scope bounds.

## 2. API Backend Rollback Procedure (Oracle Cloud)

If the newly deployed `kelvin-staging-api` fails liveness or readiness checks:

```bash
# 1. Rollback container to previous certified image
docker stop kelvin-staging-api
docker rm kelvin-staging-api

# 2. Relaunch using the verified rollback image
docker run -d \
  --name kelvin-staging-api \
  --restart unless-stopped \
  --network kelvin-network \
  --env-file /etc/kelvin/staging.env \
  -p 127.0.0.1:8080:8080 \
  kelvin-api:rollback-auth-m8

# 3. Verify health restoration
curl -fsS http://127.0.0.1:8080/healthz
curl -fsS http://127.0.0.1:8080/readyz
```

## 3. Frontend Rollback Procedure (Vercel)

If the Vercel production frontend exhibits critical regressions:

1. Identify the previous certified deployment ID:
   ```bash
   vercel ls kelvin
   ```
2. Promote the previous known-good deployment to Production instantly:
   ```bash
   vercel alias set <previous-deployment-url> kelvin-orpin.vercel.app
   ```
3. Verify live accessibility:
   ```bash
   curl -fsS https://kelvin-orpin.vercel.app
   ```

---

## 4. Worker Daemon Rollback Procedure

If the worker daemon experiences unexpected restarts or failure:

```bash
# 1. Immediately deactivate worker service
sudo systemctl stop kelvin-worker.service

# 2. Ensure service remains disabled
sudo systemctl disable kelvin-worker.service

# 3. Kill any lingering crun/podman scanner containers
sudo podman rm -f $(sudo podman ps -aq --filter label=app=kelvin-scanner) 2>/dev/null || true
```

---

## 5. Database Rollback Guidelines

- **No Destructive Operations:** The M9 and M9.8 deployment does not apply destructive database migrations.
- If schema rollback is required, use forward-compatible non-destructive patching or restore from Supabase Point-in-Time Recovery (PITR).
