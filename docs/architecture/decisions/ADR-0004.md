## 1. Context and Problem Statement

Kelvin's frontend must serve three distinct personas (Junior AppSec Analyst, Senior Security Engineer, Compliance & Platform Administrator) with different technical proficiencies and workflows. The frontend must:

* Present a unified dashboard without overwhelming junior analysts with raw scanner logs.
* Provide granular execution controls for senior engineers.
* Deliver compliance-grade executive reporting for administrators.
* Be accessible (WCAG 2.1 AA) and keyboard-efficient.
* Remain responsive across desktop, tablet, and mobile breakpoints.

Informal UI decisions risk inconsistent UX, fragmented state management, and disconnected screens between assessment states.

## 2. Decision Drivers

| Driver | Priority | Rationale |
| :--- | :--- | :--- |
| Role-scoped views & information architecture | Critical | Each persona sees only relevant controls (PERSONAS.md §5.1). |
| WCAG 2.1 AA accessibility | Critical | Legal and inclusion requirement (PERSONAS.md §6.1). |
| Keyboard efficiency & focus management | High | Security analysts operate at speed; focus traps and shortcuts required. |
| Type safety & maintainable component model | High | Reduces UI bugs that could leak data or misrepresent findings. |
| Real-time job status streaming | High | WebSocket connection to control plane for live assessment telemetry. |
| Design system consistency | High | Prevents divergent visual patterns across screens. |
| Bundle size & load performance | Medium | Fast time-to-interactive for analysts under time pressure. |

## 3. Considered Alternatives

| Alternative | Pros | Cons | Verdict |
| :--- | :--- | :--- | :--- |
| **React + TypeScript + Tailwind CSS + shadcn/ui (Radix primitives)** | Strong ecosystem; TypeScript type safety; accessible Radix primitives (WCAG-friendly); Tailwind design-system friendly; large hiring pool; excellent client-side state management | React ecosystem churn; bundle size (mitigated with code splitting) | **Selected** |
| Vue.js + TypeScript + Vuetify / Element Plus | Gentle learning curve; good accessibility components; performant | Smaller ecosystem for advanced data grids/charts; fewer accessibility audits of component libraries | Rejected |
| Angular + Angular Material | Opinionated; built-in accessibility; enterprise-grade | Heavy bundle; steeper learning curve; less design-system flexibility | Rejected |
| Svelte + SvelteKit | Small bundle; reactive by default; good performance | Smaller ecosystem; fewer enterprise accessibility component libraries; smaller hiring pool | Rejected (Phase 6 candidate) |
| Server-side rendered (Next.js / Remix) | SEO not relevant for authenticated dashboard; SSR adds complexity for an SPA behind auth | Unnecessary complexity; authenticated dashboard benefits from client-side hydration | Rejected |

## 4. Decision

Kelvin's frontend is a **Single Page Application (SPA) built with React + TypeScript**, styled with **Tailwind CSS**, using **accessible UI primitives (shadcn/ui built on Radix UI)** for the component foundation, and **TanStack Query (React Query)** for server-state management.

**Key constraints:**
* TypeScript strict mode enabled; all props and API responses typed.
* Component library restricted to Radix primitives + Tailwind; no ad-hoc CSS or third-party component libraries without ADR amendment.
* WCAG 2.1 AA conformance: contrast ≥ 4.5:1, visible focus indicators, ARIA labels, keyboard-navigable, screen-reader tested (NVDA/JAWS/VoiceOver).
* Role-scoped navigation (PERSONAS.md §5.1): Compliance Admin sees audit/reporting views; Engineer sees worker/profile views; Analyst sees assessment/findings views.
* Real-time job status via WebSocket to the API gateway (WSS).
* Code-split by route; lazy-load heavy components (data grids, report viewers).
* State management: React Query for server state; React Context/Zustand for minimal UI state; no Redux unless justified by ADR amendment.

**Design system:**
* A shared design system package (`@kelvin/ui`) hosts color tokens, spacing, typography, and accessible component variants, consumed by all frontend features.

---

## 5. Consequences

### Positive Consequences
* Accessible component primitives (Radix) accelerate WCAG 2.1 AA compliance.
* TypeScript prevents entire classes of runtime type errors in findings/report rendering.
* React Query handles caching, refetching, and WebSocket status streaming cleanly.
* Role-scoped views reduce cognitive load per persona (PERSONAS.md §6).

### Negative Consequences
* React ecosystem churn requires periodic dependency review.
* Bundle size managed via code splitting; initial load may be larger than a vanilla JS app.
* Accessibility requires ongoing QA (screen-reader testing, contrast audits) — not a one-time implementation.

### Risks
* Third-party component vulnerability (mitigated: Dependabot, `npm audit`, quarterly frontend dependency review).
