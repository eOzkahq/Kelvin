## 1. Context and Problem Statement

Kelvin requires a relational persistence layer for tenants, users, projects, assets, assessments, jobs, findings, reports, and the immutable audit trail. The data model is highly relational (tenant → project → asset → assessment → job → finding → evidence), requires ACID transactions for job state transitions, and must enforce row-level tenant isolation to prevent cross-tenant data leakage.

The choice must also support structured migration tooling so schema changes are version-controlled, reviewable, and reproducible across environments.

---

## 2. Decision Drivers

| Driver | Priority | Rationale |
| :--- | :--- | :--- |
| ACID transactions for job state machine | Critical | Assessment lifecycle must transition deterministically; no partial states. |
| Row-level tenant isolation | Critical | Multi-tenant separation is a security requirement (THREAT_MODEL T-08). |
| Relational data model fidelity | High | Assessment graph (asset→job→finding→evidence) is inherently relational. |
| Immutable audit trail append-only semantics | High | Legal defensibility requires tamper-evident, append-only records. |
| Structured, version-controlled migrations | High | Schema changes must be reviewable and reproducible. |
| Operational simplicity (single engine) | High | Avoids redundant data stores and consistency complexity. |
| Encryption at rest & in transit | High | Confidential vulnerability data must be protected. |

---

## 3. Considered Alternatives

| Alternative | Pros | Cons | Verdict |
| :--- | :--- | :--- | :--- |
| **PostgreSQL 15+ + pg_migration / golang-migrate** | Mature, ACID-compliant; row-level security (RLS) policies; JSONB for semi-structured findings; strong encryption; rich migration tooling; wide operational expertise | Single primary write node (mitigated with read replicas); vertical scaling limits (mitigated by partitioning) | **Selected** |
| MySQL / MariaDB | Mature; wide adoption | Weaker RLS implementation; less advanced JSONB; audit-log extensions less mature | Rejected |
| MongoDB | Flexible schema; horizontal scaling | Not ACID-compliant across documents (prior to recent versions, limited transactions); no native row-level tenant isolation; schema-less design risks inconsistent findings data | Rejected |
| CockroachDB | Distributed SQL; strong consistency; multi-tenant by design | Higher operational complexity; over-engineered for Phase 1 single-node deployment; smaller DBA talent pool | Rejected (Phase 4/6 candidate for multi-region) |
| SQLite | Zero-config; single file | No concurrent multi-tenant server access; no network security model; unsuitable for multi-worker platform | Rejected |

---

## 4. Decision

Kelvin's relational persistence layer is **PostgreSQL 15+** (or later LTS), deployed as a managed service or self-hosted with the following constraints:

**Schema & data modeling:**
* Core entities: tenants, users, projects, assets, assessments, jobs, findings, evidence, reports, audit_log.
* Every tenant-owned table includes `tenant_id` with a row-level security (RLS) policy enforcing `tenant_id = current_tenant_id()`.
* Finding records use JSONB for semi-structured scanner-specific fields while keeping core fields (fingerprint, severity, confidence, cwe_id, affected_target) as typed columns.
* Audit log table is append-only: no UPDATE/DELETE privileges granted to application roles; inserts only via a dedicated audit service account.

**Migration tooling:**
* **golang-migrate** (or equivalent Go-native migration tool) with SQL migration files versioned in `db/migrations/`.
* Migrations are reviewed in pull requests and applied via CI/CD; no ad-hoc `ALTER TABLE` outside migration files.
* Each migration is idempotent where possible and includes a down migration for rollback.

**Security:**
* TLS 1.3 required for all client-to-database connections.
* Encryption at rest via platform-native PostgreSQL encryption (PGTransit / TDE or cloud provider equivalent).
* Application connects via a least-privilege database role; no superuser access from application code.

---

## 5. Consequences

### Positive Consequences
* ACID guarantees ensure deterministic job state-machine transitions.
* Row-level security enforces tenant isolation at the database layer (defense in depth).
* JSONB balances structured queries with flexible scanner-specific finding data.
* Mature operational tooling (backups, PITR, replication, monitoring).

### Negative Consequences
* Single-primary write bottleneck for very high write volumes (mitigated with read replicas for reports/analytics).
* Requires DBA-level operational knowledge for tuning and RLS policy management.

### Risks
* RLS misconfiguration leading to cross-tenant leakage (mitigated: automated tenant-isolation tests in CI, quarterly penetration tests).

## 7. Notes

CockroachDB remains a Phase 4/6 candidate if multi-region active-active deployment becomes a requirement. Migration from PostgreSQL to CockroachDB would be facilitated by keeping SQL standard compliance and avoiding PostgreSQL-specific extensions beyond RLS and JSONB.
