## 1. Context and Problem Statement

Kelvin executes third-party scanner binaries (Nmap, Nuclei, OpenVAS, Trivy, etc.) inside worker nodes against potentially hostile target hosts. A scanner vulnerability, malicious target response, or misconfigured check could lead to container breakout, host-node compromise, SSRF into internal infrastructure, or credential exfiltration. Workers must be disposable, rootless, and strictly egress-bounded so that a compromised worker cannot reach the control plane or internal networks.

---

## 2. Decision Drivers

| Driver | Priority | Rationale |
| :--- | :--- | :--- |
| Container breakout prevention | Critical | THREAT_MODEL T-13: scanner RCE must not compromise the host. |
| Network isolation from control plane | Critical | THREAT_MODEL T-14: workers must not reach internal/control-plane CIDRs. |
| Rootless execution | High | No container process runs as root (UID ≠ 0). |
| Bounded compute & execution time | High | Prevents DoS via CPU/memory exhaustion or hung sockets (T-10, T-11). |
| Disposable, ephemeral filesystem | High | No persistent state on worker; fresh filesystem per job. |
| Scanner adapter portability | High | Third-party CLI tools run unchanged inside the container. |
| Observable worker health | High | Heartbeats and exit codes feed the job state machine. |

---

## 3. Considered Alternatives

| Alternative | Pros | Cons | Verdict |
| :--- | :--- | :--- | :--- |
| **Rootless Docker (Podman-compatible) + seccomp/AppArmor** | Industry-standard container isolation; rootless user namespaces; seccomp/AppArmor profiles; read-only root FS; mature tooling; Go-compatible | Container escape vulnerabilities still possible (defense in depth required); Docker daemon absent in rootless mode | **Selected** |
| gVisor / Kata Containers | Stronger kernel isolation (sandboxed kernel / VM per container) | Higher overhead; slower cold start; more complex networking; overkill for Phase 1 single-node | Rejected (Phase 4+ high-assurance candidate) |
| Wasm / WebAssembly workers | Tiny attack surface; fast cold start | Limited scanner binary support (most scanners are native x86/ARM); immature ecosystem | Rejected (Phase 6 candidate) |
| Bare-metal / uncontainerized scanners | Maximum performance | No isolation; total host compromise risk | Rejected (violates T-13) |
| Privileged Docker containers | Full scanner compatibility | Total host compromise risk; violates rootless principle | Rejected |

---

## 4. Decision

Kelvin scanner workers execute as **rootless containers** (Docker/Podman-compatible, OCI runtime) with the following mandatory hardening profile:

**Container runtime:**
* Rootless execution: container runs as a non-root user inside user-namespace-remapped container (container UID 0 maps to unprivileged host UID).
* No `--privileged`; no Docker socket mount; no host PID/IPC/UTS namespace sharing.
* `--read-only` root filesystem; ephemeral `tmpfs` mounts for `/tmp` and `/run` with `noexec` where possible.
* Non-root user inside the container (`USER` directive in Dockerfile).

**Security profiles:**
* seccomp profile restricting dangerous syscalls (mount, ptrace, reboot, module loading, clock adjustments).
* AppArmor profile (or SELinux equivalent) restricting file, network, and process operations.
* Seccomp/AppArmor profiles versioned and reviewed alongside scanner adapter changes.

**Resource & execution bounds:**
* Memory limit (cgroups v2) per worker profile (see SCAN_PROFILES.md execution_budget).
* CPU quota/cores limit per worker.
* `pids-limit` to prevent fork bombs.
* Hard execution deadline enforced by the worker supervisor (process killed at `hard_execution_deadline_seconds`).
* Read/connection timeouts on all scanner adapter network calls.

**Network:**
* Egress proxy allows only verified target IPs/domains (SYSTEM_ARCHITECTURE.md NB-05).
* RFC 1918, loopback (`127.0.0.0/8`), link-local (`169.254.0.0/16`), and cloud metadata (`169.254.169.254`) blocked at egress proxy.
* Pinning DNS resolver (anti-rebind; TTL=0; single resolution at validation time).
* Worker initiates no inbound connections; outbound only to broker (jobs/heartbeats) and FindingsSvc (sanitized results).

**Scanner adapters:**
* Third-party binaries distributed as versioned, signed container images (Cosign signing, ADR-0003 supply chain).
* Adapters run unprivileged; scanner output is streamed to FindingsSvc only after schema validation and credential redaction (SCAN_PROFILES.md §6).

## 5. Consequences

### Positive Consequences
* Container breakout is contained: compromised worker has no host credentials, no Docker socket, and no host namespace access.
* Network isolation prevents SSRF and internal pivoting (T-13, T-14).
* Disposable filesystem ensures no residual state or credentials persist between jobs.
* Bounded resources prevent worker-driven DoS of the host node.

### Negative Consequences
* Rootless container networking can be more complex (port binding, user namespace setup).
* Some scanner binaries expect root (e.g., raw socket scanning with Nmap); these require capability grants (`CAP_NET_RAW`) reviewed case-by-case, or are excluded from rootless workers.
* Stronger isolation (gVisor/Kata) deferred increases theoretical breakout risk vs. VM-per-container (mitigated by defense-in-depth: seccomp + AppArmor + egress blocking).

### Risks
* New container escape CVEs (mitigated: quarterly container runtime security review, CVE monitoring, rapid patching).

## 7. Notes

gVisor or Kata Containers remain Phase 4+ candidates for high-assurance multi-tenant deployments where stronger kernel isolation is required. The worker daemon abstracts the container runtime behind an interface, allowing runtime migration via future ADR without changing scanner adapter code.
