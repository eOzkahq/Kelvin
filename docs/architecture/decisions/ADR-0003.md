## 1. Context and Problem Statement

Kelvin requires an asynchronous message/task broker to decouple the API control plane from sandboxed scanner workers. The broker must:

* Durably enqueue assessment jobs with execution bounds (concurrency, rate, deadline).
* Support job prioritization, delayed execution, retries, and dead-letter handling.
* Stream job state transitions (heartbeats, completion acks) to clients via WebSocket.
* Persist queued jobs across broker restarts (no lost assessments).
* Scale horizontally with the worker fleet without duplicating the control plane.

---

## 2. Decision Drivers

| Driver | Priority | Rationale |
| :--- | :--- | :--- |
| Durability & no lost jobs | Critical | Assessments must survive broker restarts. |
| Job prioritization & retries | High | High-impact assessments need scheduling; failed jobs need bounded retry. |
| Pub/sub for live job telemetry | High | Dashboard WebSocket status streaming. |
| Short-lived worker tokens | High | Workers authenticate with scoped, expiring credentials. |
| Operational simplicity | High | Single broker engine preferred over redundant messaging systems. |
| Go client maturity | High | Backend is Go (ADR-0001); client library must be production-grade. |

---

## 3. Considered Alternatives

| Alternative | Pros | Cons | Verdict |
| :--- | :--- | :--- | :--- |
| **Redis + BullMQ (or Go-native redis queue)** | Mature pub/sub; durable job queues with RDB/AOF persistence; excellent Go client (`redis/go-redis`); prioritization, delayed jobs, retries, dead-letter lists; low operational overhead; single engine | Redis is in-memory by default (mitigated with persistence config); single-threaded command processing (adequate for control-plane job rates) | **Selected** |
| RabbitMQ (AMQP) | Mature AMQP; robust routing; dead-letter exchanges; clustering | Additional operational dependency; AMQP client complexity; no native pub/sub-to-WebSocket bridge; more operational surface than Redis | Rejected |
| Apache Kafka | High throughput; durable log; replayable | Over-engineered for control-plane job queue; high operational overhead; exactly-once semantics complexity | Rejected (Phase 6 event-streaming candidate) |
| NATS JetStream | Lightweight; durable streams; good Go client | Smaller operational footprint than Redis but less community tooling for job queues; newer ecosystem | Rejected (Phase 4+ candidate) |
| PostgreSQL LISTEN/NOTIFY + jobs table | No new dependency; ACID | Polling overhead; limited priority/delay/retry features; couples job queue to primary DB | Rejected (hybrid: DB stores job state; Redis brokers execution) |

---

## 4. Decision

Kelvin's distributed job queue and state broker is **Redis (7+) with a BullMQ-compatible job queue pattern**, implemented via Go-native Redis client (`redis/go-redis`).

**Configuration:**
* Persistence enabled: RDB snapshots + AOF (appendonlyfsync everysec) for crash durability.
* Maxmemory policy: `noeviction` (jobs must never be silently dropped due to memory pressure).
* TLS 1.3 for all client-to-Redis connections; Redis ACLs for least-privilege access (separate roles for orchestrator, workers, findings service).
* Redis Sentinel or managed Redis with failover for high availability.

**Architecture note:** Job *state* (assessment record, status transitions) remains the source of truth in PostgreSQL (ADR-0002). Redis is the *execution broker* for job dispatch, heartbeats, and real-time status streaming. On broker restart, jobs are reconciled from PostgreSQL.

**Worker authentication:**
* Workers connect to Redis with short-lived, job-scoped tokens issued by the Job Orchestrator.
* Tokens are bounded to a single job ID and expire after the hard execution deadline.

---

## 5. Consequences

### Positive Consequences
* Durable, prioritized job queue with retries and dead-letter handling.
* Pub/sub enables real-time job status streaming to the dashboard via WebSocket.
* Single operational engine (Redis) reduces complexity vs. multiple messaging systems.
* Mature Go client integrates with ADR-0001 backend.

### Negative Consequences
* Additional operational dependency to monitor and back up.
* Redis memory usage grows with queued job volume (mitigated: bounded queue depth, per-tenant quotas from SCAN_PROFILES.md).

### Risks
* Redis outage blocks new assessment dispatch (mitigated: Sentinel/HA, jobs retained in PostgreSQL for replay).

## 7. Notes

NATS JetStream remains a Phase 4+ candidate if lightweight distributed streaming becomes necessary. The queue abstraction layer in Go isolates the control plane from the specific broker implementation, allowing future migration without rewriting service code.
