## 1. Context and Problem Statement

KELVIN has completed its feature implementation and quality assurance verification across Phases 1 through 4, culminating in the pre-Phase 5 audit approval (`PRE-P5-01`). To safely release KELVIN into production, the platform must operate on an immutable, defensible, and resilient deployment topology.

The key security and operational challenges are:
1. **Hostile Target Blast Radius:** Security scanners execute tests against external and internal customer targets that may attempt exploitation, packet sniffing, or local service reflection.
2. **Privilege Over-Assignment:** If worker processes or containerized scanners have direct access to the database or cloud credentials, any compromised scanner process compromises tenant data.
3. **Availability Under Spikes:** Long-running security assessments must not degrade the latency or responsiveness of the web UI or REST API control plane.
4. **Tenant Isolation:** Multi-tenant customer data must remain strictly isolated at the compute, network, and database layers.

---

## 2. Decision Drivers

- **Zero-Trust Network Segmentation:** Isolate edge ingress, stateless API control plane, async workers, sandboxed scanner containers, and persistence tiers into distinct subnets.
- **Least Privilege for Execution:** Ephemeral scanner containers must have no access to the primary database, no AWS/cloud IAM admin roles, and drop all Linux capabilities.
- **Predictable Blast Radius:** An out-of-memory error, network hang, or process crash in a scanner adapter must not impact other concurrent assessments or the control plane.
- **High Availability & Fault Tolerance:** Multi-AZ deployment (minimum 3 AZs in production) with automated failover for all control-plane and data tiers.
- **Reproducible Topology:** Staging and Production must share identical architecture and configuration paradigms, differing only in instance scale and redundancy.

---

## 3. Considered Options

| Option | Advantages | Disadvantages | Verdict |
| :--- | :--- | :--- | :--- |
| **Option A: Monolithic Shared Compute** (API and scanner workers co-located on identical virtual nodes with direct DB access) | Lowest initial complexity; minimal networking configuration | High blast radius; scanner crash or resource exhaustion degrades API; critical security risk if scanner binary is compromised | **Rejected** |
| **Option B: Isolated Micro-Modular Segmentation with Sandboxed Execution** (Stateless Go API in private app subnets, queue-driven workers in worker subnets, rootless ephemeral scanner containers in isolated subnets with egress NAT, and database in segregated subnets) | Maximum security posture; bounded blast radius; independent autoscaling; strict least-privilege enforcement | Requires multi-subnet VPC design, PgBouncer pooling, and structured queue mediation | **Approved** |
| **Option C: Serverless-Only Execution** (AWS Lambda / Cloud Run for all APIs and scans) | Zero server management; granular per-second billing | Assessment runtimes frequently exceed serverless function execution limits (15 minutes); high cold-start latency; complex raw networking and proxy routing | **Rejected** |

---

## 4. Decision

We adopt **Option B: Isolated Micro-Modular Segmentation with Sandboxed Execution**.

The production environment topology is structured into five distinct operational zones:
1. **Zone 0 (Edge DMZ):** Public subnets hosting Cloudflare/WAF, CDN, and Application Load Balancers terminating TLS 1.3 with strict HSTS.
2. **Zone 1 (Application Control Plane):** Private multi-AZ subnets hosting autoscaled, stateless Go API pods and PgBouncer connection poolers. No direct public internet ingress or egress.
3. **Zone 2 (Asynchronous Worker Fleet):** Private multi-AZ subnets hosting worker orchestrators and Redis Sentinel / Valkey task queue cluster.
4. **Zone 3 (Scanner Execution Sandbox):** Isolated subnets hosting rootless, ephemeral scanner containers. Zero access to internal VPC subnets (`10.0.0.0/16`), rootless UID (`10001`), read-only root filesystems, all Linux capabilities dropped, outbound egress mediated via fixed NAT gateways.
5. **Zone 4 (Data & Persistence):** Isolated multi-AZ subnets hosting PostgreSQL 16 primary/standby instances and encrypted S3/MinIO evidence storage. Accessible solely by Zone 1 (API/PgBouncer) and S3 presigned URLs.

---

## 5. Consequences

### Positive Consequences
- **Compromise Containment:** Even if an external target exploits a scanner tool binary (e.g., memory corruption in an assessment parser), the attacker is trapped inside an unprivileged sandbox with no database routes, no metadata service access, and no internal credentials.
- **Elastic Operational Scaling:** Heavy scanning workloads scale horizontally via KEDA queue metrics without starving the Go API or UI dashboard of CPU or memory.
- **Reliable Uptime:** Multi-AZ distribution ensures 99.95% control plane availability and automatic database failover within 30 seconds.

### Operational Responsibilities & Costs
- Requires ongoing monitoring of Redis queue depth, worker pool latency, and PgBouncer connection limits.
- Requires maintenance of Infrastructure as Code (Terraform / OpenTofu) maintaining VPC subnets, NAT gateways, and Security Group rules across environments.
