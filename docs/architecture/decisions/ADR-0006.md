## 1. Context and problem statement

The accepted ADRs and architecture documents define the intended platform shape, while
the current repository contains a mixture of implemented libraries, incomplete runtime
wiring, and planned services. Treating a design choice as proof of deployed behavior
creates unsafe assumptions, particularly around API authorization, tenant isolation,
queue processing, and scanner containment.

The Phase 1 audit found differences between target topology and Compose/runtime wiring,
and gaps between security packages and active API paths. A subsequent readiness pass
aligned OpenAPI with registered routes, repaired worker compilation, and protected the
cancellation route; assessment persistence and scanning remain incomplete.

## 2. Decision drivers

- Keep accepted technology choices and historical decisions intact.
- Make implementation status observable and evidence-backed.
- Prevent architecture documents from declaring planned controls operational.
- Make readiness depend on code, tests, and runtime wiring rather than prose alone.

## 3. Considered options

| Option | Advantages | Disadvantages | Verdict |
| :--- | :--- | :--- | :--- |
| Treat accepted ADRs as proof of current behavior | Simple document set | Conflates design intent with implementation; hides material gaps | Rejected |
| Rewrite accepted ADRs to match current code | Makes documents look current | Erases the intended decisions and historical rationale | Rejected |
| Preserve ADR decisions and maintain a separately reviewed as-built/readiness record | Retains design history; makes gaps explicit and reviewable | Requires updates when implementation changes | Proposed |

## 4. Proposed decision

Keep ADR-0001 through ADR-0005 as records of accepted design choices. Maintain a dated
Phase Readiness Report that separately classifies each capability as **implemented and
verified**, **implemented but not runtime-wired or not verified**, **partial**, or
**planned/deferred**. Architecture diagrams must be labeled either **as-built** or
**target-state**. Documentation may claim a security control is operational only when
the active runtime path invokes it and an appropriate test or deployment verification
covers it.

Phase transitions require an explicit readiness review with named engineering and
security sign-off. A passing design review or the existence of a package, schema, or ADR
does not by itself satisfy a runtime acceptance criterion.

## 5. Consequences

### Positive consequences

- Design intent remains available without being mistaken for deployed behavior.
- Gaps become traceable remediation work and can block a phase transition explicitly.
- Security and contract claims can be checked against executable evidence.

### Costs and risks

- Readiness reports need maintenance as code and deployment evolve.
- Teams must agree on verification evidence for each control and acceptance criterion.
- This ADR is **proposed**, not yet an organizationally approved policy.
